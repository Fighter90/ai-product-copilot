# ADR-013 — Отчёты: ГОСТ-2 по эталону заказчика

- **Статус:** принято
- **Дата:** 2026-10-26
- **Контекст:** отчёт v3.0.0 — 8 страниц сплошного текста без таблиц, что не соответствует
  ожиданиям заказчика. Эталон — `ProductCamp_Аналитический_отчет.docx` (разобран распаковкой
  OOXML): 97 таблиц, настоящее TOC-поле, приложения А–Я, оформление в духе ГОСТ Р 7.32-2017.
  Полный разбор расхождений и критерии приёмки —
  `openspec/changes/report-gost-v2/proposal.md` (8 расхождений: синие H1, нет таблиц,
  нет фронт-материи, двойная нумерация карточек и др.).

## Решение

- **Структура и оформление — по эталону**, для DOCX и его PDF-зеркала одинаково:
  - титул по центру (13pt / 20pt bold), человекочитаемый период вместо UUID среза;
  - фронт-материя заголовками H1 без номеров: СОДЕРЖАНИЕ — настоящее поле
    `TOC \o "1-3" \h \z \u` (`features.updateFields`; Word предложит обновить по F9, как
    в эталоне), ПЕРЕЧЕНЬ РИСУНКОВ, ОБОЗНАЧЕНИЯ/ТЕРМИНЫ, ВВЕДЕНИЕ, УПРАВЛЕНЧЕСКОЕ РЕЗЮМЕ;
  - сквозная нумерация разделов с 1: H1 КАПСОМ «1 КОНТЕКСТ…» (номер без точки), подразделы
    H2 «N.M» (карточки гипотез — подразделы своего раздела);
  - таблицы — настоящие `<w:tbl>` с рамками и подписью «Таблица N.M — …» над таблицей;
  - подписи «Рисунок N — …» под графиками, дублирующиеся в перечне рисунков;
  - каждый крупный блок — с новой страницы; чёрные заголовки, точные ГОСТ-поля (twips).
- **Детерминизм сохраняется**: контент — чистые функции от `ReportSnapshot` через
  `report-sections.ts`, единый источник для DOCX/PDF/превью. Все числа таблиц и подписей —
  из того же снапшота, что и текст (инвариант `factsource`); в render-пути нет LLM и
  `Date.now()` — DOCX и PDF из одного `snapshotId` остаются идентичными по контенту.
- **Верификатор `scripts/verify-report-gost.mjs`** — 14 проверок собранного DOCX
  (unzip → регэкспы по XML, без внешних зависимостей): поля страницы, A4, Times New Roman,
  кегль 14pt, межстрочный 1.5, отсутствие синих заголовков, PAGE-поле в футере, рамки таблиц,
  подписи рисунков, обязательные разделы. Запускается **вручную в CI-цикле**
  (`node scripts/verify-report-gost.mjs <docx>`), вердикт PASS/PASS-WITH-WARNINGS/FAIL.

## Обоснование

- Эталон заказчика — не вкусовщина, а рабочее требование: отчёт пойдёт в поставку, и его
  оформление сверяют с ГОСТ-образцом. Проще привести генератор к эталону, чем спорить о стилях.
- Сборка отчёта осталась детерминированной: tables/figures — новые поля `ReportSection`
  (опциональные, обратная совместимость), заполняются теми же агрегатами снапшота
  (`channelTotals`, `s.kpi`, `s.breakdowns`). Это сохраняет инвариант ADR-008 «DOCX==PDF»
  и зелёный `factsource-invariant`.
- Ручной CI-шаг вместо автотеста: верификатор требует собранный DOCX-артефакт (полный цикл
  сборки со снапшотом и Puppeteer) — прогонять его на каждый push дороже, чем на срез релиза.
  Юнит-инварианты тем временем покрыты тестами (`docx.test.ts`, `pdf.test.ts`).

## Последствия

- **Результат: верификатор PASS 14/14; PDF-зеркало — 43 страницы** (против 8 в v3.0.0),
  структура и нумерация совпадают с эталоном.
- **Новые разделы отчёта добавляются только через `report-sections.ts`** + обновление
  верификатора, если раздел обязателен по ГОСТ: список проверок в шапке скрипта — контракт
  структуры. Секция, добавленная в обход, выпадет из TOC/перечня и не пройдёт верификацию.
- TOC-поле пусто до обновления полей Word (F9 при первом открытии) — известное ограничение
  OOXML, принятое как в эталоне; PDF использует статический список разделов.
- Приложения А…Я и полные выгрузки — вне этой итерации: снапшот хранит только агрегаты и
  top-5 срезы, потребуется отдельное изменение модели данных.

## Альтернативы

- **Оставить данные текстом (v3.0.0)** — отклонено: прямое расхождение №4 с эталоном.
- **Генерировать отчёт LLM на основе снапшота** — отклонено: ломает детерминизм
  (DOCX ≠ PDF из одного `snapshotId`), нарушает инвариант factsource.
- **Верификатор как автотест в CI на каждый push** — отклонено пока: требует полного цикла
  сборки с браузером; пересмотр при выносе сборки отчёта в отдельный job.
