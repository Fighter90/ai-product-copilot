# Формулы и расчёты

Каждая цифра кабинета детерминирована: чистые функции от данных БД, без случайности и
скрытых множителей. Рядом с формулой — файл-источник, чтобы всегда можно было сверить.

## Трафик и конверсии

| Величина | Формула | Пример |
| -------- | ------- | ------ |
| **Визиты за период** | Σ `channel_stats.visits` по датам периода | 12–25 окт: Σ по всем каналам и дням |
| **CR канала** | `goal_reaches / visits` | 420 визитов, 12 заявок → CR = 12/420 = **2,86 %** |
| **CR страницы** | `goal_reaches / visits` из `page_stats` | `/lp`: 14/380 = **3,68 %** |
| **Доля канала** | `visits канала / Σ visits` | podcast 420 из 680 → **61,8 %** |

Источник: `code/backend/src/db/repositories/metrics-repo.ts`, `code/shared/src/aggregate.ts`.
Фильтр роботов применяется на уровне счётчика (не на разбивках) — иначе строки теряются
(ANA-65).

## Воронка и KPI

| Величина | Формула | Пример |
| -------- | ------- | ------ |
| **B2C-заявки** | Σ `goal_reaches` основной цели за период | 30 заявок |
| **Оплачено B2B** | Σ `tickets` сделок в стадии `paid` | 20 билетов |
| **Оплачено всего** | `b2c_payments.tickets` (по дням) + Σ билетов оплаченных B2B-сделок | 12 + 20 = **32** |
| **Gap до цели** | `max(0, target − оплачено)`, где «оплачено» = B2B paid **+ заказы Метрики**, если основная цель — тип «оплата» (`goalLabel.isPaid`) | target 300, 20+47 → gap **233** |

Источники: `code/backend/src/report/snapshot-builder.ts` (строки 92–105),
`code/backend/src/routes/payments.ts` (`/payments/summary`). Инвариант: **заявка ≠ оплата** —
B2C-заявки никогда не складываются с деньгами.

## Прогноз и «Что если» (страница KPI)

Модель прогноза — линейная экстраполяция текущего темпа:

1. **Темп оплат** = оплачено за период / дней в периоде.
2. **Дней до дедлайна** = дата цели − сегодня.
3. **Прогноз** = оплачено + темп × дней до дедлайна.
4. Слайдер «Доп. трафик +N %» пропорционально увеличивает заявицы (`заявки × (1+N/100)`), слайдер
   «Рост CR +N п.п.» — конверсию; обе проверки пересчитывают воронку визит → заявка → оплата.

Ограничения: прогноз не знает о сезонности — используйте «Что если» для сценариев, а не
обещаний. Источник: `code/frontend/src/routes/goals.tsx`, `code/shared/src/period-totals.ts`.

## Гипотезы: ICE

```
ICE = Impact × Confidence × Ease        (каждый множитель 1–10)
```

- **Impact** — насколько сильно повлияет на метрику, если гипотеза верна;
- **Confidence** — насколько уверены, что сработает (данные Метрики, кейсы, кастдев);
- **Ease** — насколько легко проверить/внедрить.

Каждый множитель обязан иметь текстовое обоснование. Сортировка ICE-таблицы — по убыванию
итога. Источник: `code/shared/src/validation.ts`, страница `/app/hypotheses`.

## Маркетинговая сетка (недели)

Агрегация — по неделям листа «стата» (не по календарным):

| Строка | Формула недели [start … end] |
| ------ | ---------------------------- |
| заходы на лендос | `Σ channel_stats.visits` где `date ∈ [start, end]` |
| цели на сайте | `Σ channel_stats.goal_reaches` за ту же неделю |
| оплат | `Σ b2c_payments.tickets` + `Σ b2b_manual.tickets` где `date_paid` в неделе |
| Заявки b2b | `COUNT(b2b_manual)` где `date_added` в неделе |
| остальные | вручную (аналитик) или импорт из листа |

Правило записи: weekTotals считаются только при наличии исходных данных в окне — неделя без
данных остаётся пустой. Источник: `code/backend/src/marketing/sync.ts`,
`marketing-repo.ts → weekTotals()`.

## Покрытие данных и гэпы

Дырой считается пропуск **≥ 3 календарных дней** между соседними датами с событиями внутри
одного ряда (b2b `date_added`, b2b `date_paid`, дни `b2c_payments`). Пример: события 09.10 и
19.10 → дыра 9 дней. Проверка: `GET /api/payments/coverage`. Источник:
`code/backend/src/data/coverage.ts`.

## Округления и форматирование

- Проценты — `Intl.NumberFormat` локали, 1 знак после запятой (`2,9 %` RU / `2.9%` EN).
- Числа — разделители тысяч по локали; длительности — `мм:сс`.
- Валютные суммы B2B — целые рубли (`amount_rub`).

Источники: `code/frontend/src/i18n/index.ts` (`fmtNum`, `fmtPct`, `fmtDate`).
