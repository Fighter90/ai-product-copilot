## 1. Роль и обязанности администратора

Администратор — владелец рабочего контура. Зоны ответственности:

| Зона         | Обязанности                                                                            |
| ------------ | -------------------------------------------------------------------------------------- |
| Люди         | заводить/деактивировать пользователей, раздавать роли, сбрасывать пароли               |
| AI           | поддерживать цепочку провайдеров (ключи, порядок, проверки), следить за использованием |
| Данные       | токен Метрики, цели, SMART-цель и дедлайн, регулярный sync, резервный аккаунт          |
| Интеграции   | DataLens (публичный API, токен)                                                        |
| Эксплуатация | следить за health, бэкапами, версиями; деплой новых релизов                            |
| Безопасность | секреты только в `.env`; ротация паролей; audit log под контролем                      |

Вход: тот же `/login`; в сайдбаре появляется группа **АДМИНИСТРИРОВАНИЕ**.

## 2. Первичная настройка (чек-лист)

```text
□ 1. Задать /opt/pca/.env на сервере: METRIKA_OAUTH_TOKEN, COUNTER_ID, APP_SECRET,
     DEMO_*_PASSWORD (или DEMO_USERS=0), AI-ключи (или настроить позже в админке)
□ 2. Задеплоить: SSH_KEY=~/.ssh/pca_deploy ./deploy/deploy.sh → health = версии
□ 3. Войти админом (первый пользователь создаётся из ADMIN_EMAIL/ADMIN_PASSWORD при
     пустой таблице users)
□ 4. Пользователи → завести аналитиков (временный пароль показывается один раз!)
□ 5. AI-провайдеры → добавить провайдеров, проверка связи, включить
□ 6. Метрика → проверить токен, выбрать KPI-цель, задать дедлайн (SMART)
□ 7. Запустить sync (или дождаться ночного) → проверить Обзор
□ 8. Собрать первый отчёт → Export DOCX/PDF (проверить детерминизм: ×2)
□ 9. DataLens → подключить (опционально)
□ 10. Бэкапы → проверить timer и свежую копию /opt/pca/backups
```

## 3. Пользователи и роли (`/app/admin/users`)

### 3.1 Создание

Кнопка **«Новый пользователь»**: Email · Имя · Роль (Администратор/Аналитик). Система генерирует **временный пароль и показывает его один раз** — скопируйте и передайте защищённым каналом (не по открытому чату!). При следующем входе пароль запрашивается как есть (отдельного «смените пароль» экрана нет — см. 3.4).

### 3.2 Роли

- **Администратор** — всё, включая админку и настройки.
- **Аналитик** — мониторинг/аналитика/работа, без админки (прямые URL дают «Нет доступа»).

Смена роли: кнопка `Изменить роль` у строки (aria-label `Изменить роль`); **у каждого пользователя ровно один бейдж роли** — если видите два, это баг (ANA-175).

### 3.3 Деактивация

Кнопка деактивации мгновенно отзывает сессии пользователя (вход невозможен, данные остаются). Не удаляйте пользователей, у которых есть гипотезы/решения/сделки — деактивируйте.

### 3.4 Сброс пароля

Кнопка **«Сбросить пароль»** выпускает новый временный пароль (показывается один раз) и **завершает все сессии** пользователя. Отдельной формы «забыл пароль» нет — сброс делает администратор.

### 3.5 Демо-аккаунты

`admin@dashboardcamp.ru` и `analyst@dashboardcamp.ru` создаются при первом старте с пустой таблицей users, если `DEMO_USERS=1` и заданы `DEMO_*_PASSWORD`. Пароль существующего демо-аккаунта **не меняется от правки `.env`** — ротация делается по runbook (см. [Безопасность](#10-безопасность-и-секреты)).

## 4. AI-провайдеры (`/app/admin/ai`)

### 4.1 Как работает цепочка

Запрос AI-анализа идёт по цепочке в порядке приоритета: первый активный и не-исключённый провайдер отвечает; при ошибке — исключается и вызывается следующий. Атрибуция (кто реально ответил) видна в UI отчёта («сгенерировано …») и в `ai_usage`.

### 4.2 Карточка провайдера

| Поле                  | Значение                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| Название              | отображаемое имя (OpenRouter, Anthropic, YandexGPT, GigaChat…)                                            |
| Base URL              | endpoint API провайдера                                                                                   |
| Модель                | идентификатор модели (`anthropic/claude-…`, `openai/gpt-…`, `yandexgpt/…`)                                |
| API-ключ              | вводится один раз, **маскируется навсегда** (`••••073e`, `sk-a****`); хранится зашифрованным app-секретом |
| Включён               | участвует в цепочке                                                                                       |
| Признак исключённости | «последняя проверка неуспешна — провайдер исключён из цепочки» / «ключ не настроен»                       |

### 4.3 Проверка и использование

- Кнопка **проверки связи** шлёт тестовый запрос; успех → «проверка OK <дата>», неуспех → причина (например, HTTP 400 credit balance) и исключение из цепочки.
- Блок **«Использование за 30 дней»** (`ai_usage`): вызовы/ошибки по провайдерам (пример: OPENROUTER 372 вызовов · 56 ошибок; YANDEXGPT 45·2; ANTHROPIC 28·14; GIGACHAT 9·2) — по нему видно, кто реально живой.
- Изменения настроек провайдера — **осознанное действие**: перед сохранением проверьте ключ; тестовый прогон дешевле, чем битый отчёт.

### 4.4 Рекомендации

- Держите ≥2 активных провайдеров (fallback на случай исчерпания баланса).
- Anthropic прямой — только если есть оплаченный баланс; иначе держите исключённым (цепочка пойдёт через OpenRouter).
- Ключи не пересылайте по чату — вводите прямо в админке.

## 5. Яндекс.Метрика и данные (`/app/admin/metrika`)

### 5.1 Подключение и токен

- `METRIKA_OAUTH_TOKEN` в `/opt/pca/.env` — OAuth-токен аккаунта с доступом к счётчику. Кнопка проверки токена в админке валидирует его запросом к API.
- **Резервный аккаунт**: `METRIKA_BACKUP_*` (OAuth-токен или ClientID/Secret + Verification Code). Клиент автоматически повторяет запрос под резервным токеном при отказе основного — нечувствительно для пользователей.
- `COUNTER_ID` — номер счётчика; `GOAL_ID=0` — авто-выбор платёжной цели (`goal-classifier`), или явный id.

### 5.2 Синхронизация

- Sync тянет полный набор агрегатов Reporting API по дням (дневные чанки — корректная атрибуция), сохраняя **сырые ответы** в `raw_responses`.
- Повторный sync безопасен: дозаполняет историю по ключам (даты), не затирая прошлое.
- Данные за сегодня приходят с лагом — рабочий режим «вчера и раньше».
- Не запускайте sync вручную чаще необходимого: квоты Reporting API не бесконечны.

### 5.3 Цели

- Таблица целей с ролями в воронке: `reg_open` (регистрация) → `cart_open` (корзина) → `reg_step1` (заявка) → оплата (e-commerce).
- **Архивные цели** (`ARCHIVED_GOAL_ID_THRESHOLD`) отделяются от живых; в UI включаются чекбоксом «Архивные цели».

### 5.4 Цель и SMART

Поле **«Цель (платных билетов)»** + **дедлайн** формируют SMART-строку: «Достичь ≥300 платных билетов к 21.11.2026». Кнопка **«Сбросить цель»** возвращает цель к дефолту (300). Эти значения едут в отчёт (раздел KPI) и в снапшоты (закреплённые `kpi_target`/`kpi_paid`).

⚠️ Изменение цели задним числом не пересчитывает старые снапшоты — они фиксируют контекст на момент сборки.

## 6. Интеграции: DataLens (`/app/admin/integrations`)

- Подключение к **DataLens Public API**: токен вводится в админке, сохраняется в `/opt/pca/.env` (`DATALENS_IAM_TOKEN`).
- Обновление токена: `scripts/refresh-datalens-token.mjs` — создаёт токен через `yc iam create-token` и атомарно обновляет `.env` (секреты только из окружения; пароль админа — `PCA_ADMIN_PASSWORD`, не из репозитория).
- Пользователям после подключения доступны CSV-датасеты и дашборды на странице DataLens.

## 7. Настройки KPI и цели

| Настройка              | Где                          | Эффект                                          |
| ---------------------- | ---------------------------- | ----------------------------------------------- |
| Цель (платных билетов) | админка → Метрика            | SMART-строка, плитки, план→факт, отчёт          |
| Дедлайн                | админка → Метрика            | SMART, прогноз «+N дн.», герой                  |
| Окно плана             | фиксируется при задании цели | «29 апр. 2025 → 21 нояб. 2026»                  |
| Закреплённые план/факт | `report_snapshots`           | История показывает план→факт на момент снапшота |

## 8. Журнал действий (audit log) (`/app/admin/audit`)

- Что пишется: входы/неудачные входы (`auth.login`, `auth.login_failed`), изменения пользователей, настроек, цели, провайдеров, B2B-операции.
- Загрузка асинхронная (~2–4 с); свежие записи сверху.
- Используйте при разборе инцидентов: «кто изменил цель», «когда был последний вход уволенного».

## 9. Эксплуатация: деплой, бэкапы, health

### 9.1 Health-гейт

```bash
curl -s https://dashboardcamp.ru/api/health
# {"status":"ok","service":"productcamp-analytics-backend","version":"3.4.64","build":"76d7090…","timestamp":"…"}
```

Версия+build обязаны соответствовать релизу — это критерий успешного деплоя.

### 9.2 Деплой

```bash
SSH_KEY=~/.ssh/pca_deploy ./deploy/deploy.sh
# build → rsync → restart pca-api → health-гейт
```

Переменные: `SSH_HOST` (default `root@YOUR_SERVER_IP`), `SSH_PORT`, `SSH_KEY`. GitHub Actions может быть недоступен (биллинг) — тогда деплой только так; `release.yml` добирается скриптом-комплитером.

### 9.3 Обновление версии / релиз

SemVer + conventional commits. Релиз = патч-версия → `pnpm sync-versions` → запись в `CHANGELOG.md` → тег `vX.Y.Z` → GitHub Release. Один релиз = одна задача роя (см. wiki/Swarm).

### 9.4 Бэкапы

- На сервере: `deploy/backup.sh` (systemd timer) — SQLite-копии в `/opt/pca/backups`, хранит **14** последних; лог в `backups/backup.log`, lock-файл от дублей.
- Локальная копия: `scripts/pull-backup.sh` (ssh/scp read-only, `PCA_HOST`/`PCA_KEY` из env).
- Восстановление: стоп `pca-api` → заменить `productcamp.sqlite` (+ `-wal`/`-shm`) → старт → health.

### 9.5 Статус и логи

```bash
systemctl status pca-api
journalctl -u pca-api -f
```

## 10. Безопасность и секреты

**Главное правило: секреты только в `.env` (сервер) и в локальном окружении. В репозитории и его истории их быть не должно.**

| Секрет                                    | Где                                                      |
| ----------------------------------------- | -------------------------------------------------------- |
| Токен Метрики (+ резервный), `COUNTER_ID` | `/opt/pca/.env`                                          |
| Ключи AI                                  | БД `ai_providers` (зашифрованы `APP_SECRET`), маски в UI |
| `DATALENS_IAM_TOKEN`                      | `/opt/pca/.env`                                          |
| Пароли демо                               | `/opt/pca/.env` + scrypt-хэши в `users`                  |
| `APP_SECRET`                              | `/opt/pca/.env`                                          |
| SSH-ключ деплоя                           | локальный `~/.ssh/pca_deploy`                            |

### 10.1 Ротация демо-паролей (после инцидента или планово)

Схема пароля: `scrypt$16384$saltB64$hashB64`. Сидинг создаёт демо-юзера только при отсутствии — **правка `.env` существующий пароль не меняет**. Порядок:

1. Сгенерировать хэш: `node -e "const {scryptSync,randomBytes}=require('crypto');const s=randomBytes(16);console.log('scrypt$16384$'+s.toString('base64')+'$'+scryptSync('НовыйПароль',s,64,{N:16384}).toString('base64'))"`.
2. Обновить `users.password_hash` SQL-файлом (не через shell-интерполяцию `$`!) для обоих демо-аккаунтов; `DELETE FROM sessions WHERE user_id IN (…)` — отозвать сессии.
3. Синхронизировать `/opt/pca/.env` (`DEMO_*_PASSWORD`).
4. Проверить: старый пароль → 401; новый → 200 (`POST /api/auth/login`).

Инцидент 18.11.2026: демо-пароли обнаружены в истории репо → ротированы; HEAD вычищен (env вместо хардкода). Урок: попавший в коммит пароль считается скомпрометированным навсегда — только ротация.

### 10.2 Аудит перед публикацией репо

1. `git grep` по дереву и истории: паттерны ключей (`sk-or-v1`, `sk-ant-api`, `y0_`, `AKIA`, `xox`, `BEGIN … PRIVATE KEY`), `password\s*[:=]\s*'…'`, IP сервера.
2. Проверить, что `.env`/`*.sqlite`/`*.key` никогда не коммитились (`git log --all --diff-filter=A --name-only`).
3. Workflows — только имена `secrets.*`.
4. QA-артефакты с кредами — вне git.

### 10.3 Харденинг

nginx 80/443 + HSTS; API не торчит наружу; systemd non-root + `Restart=always`; scrypt-пароли; HttpOnly-сессии с отзывом; audit log; лимит попыток входа (5).
