# OpenSpec — spec-driven процесс проекта

> 🇷🇺 Лёгкий spec-driven подход: **спецификация ДО кода**. Каталог `openspec/` с изменениями
> (`changes/`) и накопленными спецификациями (`specs/`). Внешний CLI (`openspec`, npm) не обязателен —
> структура поддерживается руками, всё живёт в репозитории.

## Зачем

- Закрывает разрыв «идея → код»: нетривиальная фича сначала описывается proposal'ом, ревьюится и
  только потом реализуется.
- Держит решения прослеживаемыми (в духе anti-hallucination проекта) и накапливает знания:
  принятые изменения переносятся в вечные спеки возможностей (`specs/<capability>/spec.md`).

## Workflow (3 шага)

### 1. Proposal — `openspec/changes/<id>/proposal.md`

Короткий документ **до кода**: зачем (проблема/контекст), что делаем (цель + вне scope),
критерии приёмки, влияние (данные/API/shared/UI/конфиг), риски и альтернативы.
Шаблон: [`changes/_template/proposal.md`](changes/_template/proposal.md).
`<id>` — kebab-case (`dual-goal-kpi`, `report-gost-v2`).

### 2. Tasks — `openspec/changes/<id>/tasks.md` (после утверждения proposal'а)

Чек-лист задач реализации (TDD-шаги: тест → код), затрагиваемые файлы, порядок работ.
По ходу реализации задачи отмечаются выполненными.

### 3. Deploy в specs — `openspec/specs/<capability>/spec.md` (после реализации)

Когда изменение реализовано и принято, его итоговое поведение переносится в спеку
соответствующей возможности (capability) — `openspec/specs/<capability>/spec.md`.
Спека описывает **текущее состояние системы** (что умеет система и по каким правилам), а не
историю работ. Затем папку изменения `changes/<id>/` можно удалить или пометить архивной.
Исторические спеки старого формата: `docs/specs/` (ссылки на них — см.
[`docs/specs/README.md`](../docs/specs/README.md)).

## Жизненный цикл изменения

`proposed` (proposal) → `approved` (+ tasks.md) → `implemented` (код влит) → перенесено в
`specs/<capability>/spec.md` → `changes/<id>/` удалено/архивировано.

## Структура каталога

```
openspec/
├── README.md            # этот файл
├── AGENTS.md            # краткие правила для AI-агентов
├── changes/             # активные и архивные изменения
│   └── _template/       # шаблон: proposal.md + tasks.md
└── specs/               # вечные спеки возможностей (текущее состояние системы)
    ├── dual-goal-kpi/   # (мигрировано из docs/specs/001)
    ├── product-overhaul/ # (мигрировано из docs/specs/002)
    └── report-gost/     # (мигрировано из docs/specs/014)
```

## Когда это обязательно

- **Обязательно:** фича затрагивает > 1 файла или > ~30 минут работы; меняет модель данных, API,
  методологию или KPI-математику.
- **Не нужно:** опечатки, разовые правки, чистка, обновление зависимостей, документация.
