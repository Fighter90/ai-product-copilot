# metrika-sync Specification

> Открытая спека возможности (OpenSpec). Источник истины — код: `code/backend/src/metrika/`
> (`sync-service.ts`, `cli-sync.ts`, `traffic-filter.ts`), `code/backend/src/routes/sync.ts`.
> Обновлена: 2026-10-27.

## Purpose

Синхронизация данных Яндекс.Метрики в SQLite: сырые ответы сохраняются в `raw_responses`
(прослеживаемость каждого числа), производные срезы пишутся по дням с историей
(`INSERT … ON CONFLICT`), повторы безопасны. Синк устойчив к сбоям API и квотам.

## Requirements

### Requirement: Синхронизация окна по дням

SyncService SHALL разбивать запрошенное окно на дневные чанки, для каждого чанка сохранять
сырой ответ Метрики в `raw_responses` (идемпотентно по `query_hash`) и записывать merged-батч
в производные таблицы (`channel_stats`, `utm_stats`, `geo_device_stats`, `page_stats`,
`exit_page_stats`) через upsert `ON CONFLICT`, не затирая предыдущие дни.

#### Scenario: Повторный синк того же окна

- **WHEN** синк запускается повторно за уже синхронизированный период
- **THEN** строки этих дней перезаписываются без дублей, а дни за пределами окна остаются неизменными

#### Scenario: Прослеживаемость

- **WHEN** любое число показано в кабинете или отчёте
- **THEN** оно выводится из срезов, соответствующих сохранённым сырым ответам в `raw_responses`

### Requirement: Валидация и устойчивость к сбоям API

Ответы Reporting API SHALL валидироваться Zod-схемами; клиент SHALL повторять временно
неудачные запросы (retry) и уважать квоты (rate-limit, опциональная пауза
`METRIKA_REQUEST_DELAY_MS` между запросами). Сбой синка SHALL NOT терять уже загруженные
данные: снимок окна удерживается в памяти, и после восстановления синк продолжается с
места останова.

#### Scenario: Квота Метрики (429) в середине окна

- **WHEN** Reporting API отвечает 429/квотой на дневном чанке
- **THEN** синк делает retry с паузой; при исчерпании попыток уже загруженные дни остаются
  в БД, а окно восстанавливается при следующем запуске без потери и дублей

### Requirement: Автоопределение KPI-цели

При `GOAL_ID=0` синк SHALL автоматически выбирать основную KPI-цель классификатором
`selectPrimaryGoal` (предпочитает цель-покупку), проверяя токен и список целей запросом
`GET goals`; явный `GOAL_ID` имеет приоритет над автоопределением.

#### Scenario: Явный GOAL_ID

- **WHEN** задан ненулевой `GOAL_ID`
- **THEN** достижения считаются по указанной цели, автоопределение не применяется

### Requirement: Доступ к синхронизации

`POST /api/sync` SHALL требовать активную сессию (роли «Аналитик» и «Администратор»);
статус последней синхронизации доступен авторизованным через `GET /api/sync/status`.

#### Scenario: Гость запускает синк

- **WHEN** запрос `POST /api/sync` без сессии
- **THEN** API отвечает 401, синхронизация не запускается

### Requirement: Срезы и фильтрация роботов

Синк SHALL наполнять пять срезов по дням: каналы (включая lastsign-каналы), UTM,
гео+устройства, страницы входа и страницы выхода; фильтрация роботов выполняется только
на уровне счётчика (не пост-фильтром по `isRobot`), чтобы не терять визиты.

#### Scenario: Данные без роботов

- **WHEN** счётчик Метрики фильтрует роботов на своей стороне
- **THEN** синк сохраняет визиты как есть, без дополнительного вычитания по `isRobot`
