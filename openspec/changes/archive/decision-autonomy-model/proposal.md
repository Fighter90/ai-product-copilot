# Proposal: decision-autonomy-model — модель «тип решения × автономия ИИ»

> Статус: `proposed` · Автор: swarm-executor (ANA-136) · Дата: 2026-11-11
> Связано: ANA-127 п.7 (админ-репорт 08.11), ANA-128 (ai-autopopulate, в проде с v3.4.6+),
> спеки возможностей: [hypotheses](../../specs/hypotheses/spec.md), [llm](../../specs/llm/spec.md)

## 1. Зачем (проблема и контекст)

ИИ-ассистент уже предлагает и оценивает гипотезы: ai-autopopulate (ANA-128) автоматически
записывает проблемные гипотезы и предложенные решения в реестр как черновики
(`decisions.source = 'ai'`, бейдж «AI» в `/app/hypotheses` и `/app/decisions`,
см. `openspec/specs/hypotheses/spec.md`). Но правил, **какие решения можно передавать ИИ**,
в системе нет:

1. Все AI-записи обрабатываются одинаково — от «посчитай разбивку оплат по каналам» до
   «поменяй цену/бюджет», хотя цена ошибки и обратимость у них несопоставимы.
2. Без границ делегирования ИИ генерирует больше черновиков, а подтверждённых гипотез
   становится меньше: PM тонет в ревью однотипного, а рискованные решения не получают
   явной эскалации человеку.
3. Эффект ИИ неравномерен по типам задач (админ-репорт 08.11, п.7): без явного контракта
   «какое решение на каком уровне автономии допустимо» время от сигнала до решения не
   сокращается без потери доли подтверждённых гипотез.

## 2. Что делаем (цель)

Ввести модель «тип решения × максимальный уровень автономии ИИ» как **статический
контракт** в `@pca/shared` (типы + матрица + чистая функция оценки), классификацию типов
в ai-autopopulate, отдавание оценки через API `/api/decisions` и бейджи в
`/app/decisions` — включая бейдж «требует PM-эскалации» с машинно-читаемой причиной для
решений, выходящих за допустимую автономию.

**Таксономия типов решений (8):** `data-analysis`, `hypothesis-draft`, `experiment-launch`,
`pricing`, `budget`, `public-comms`, `strategic`, `legal`.

**Уровни автономии ИИ:**

| Уровень | Значение                                                           |
| ------- | ------------------------------------------------------------------ |
| `A0`    | ИИ только предлагает — решает PM (подтверждение до применения)     |
| `A1`    | ИИ решает по шаблону — PM ревьюит постфактум (как ANA-128 сегодня) |
| `A2`    | ИИ автономно в лимитах (частота/объём) — **в MVP не исполняется**  |

**Статическая матрица тип → макс. автономия (MVP):**

| Тип                 | Макс. автономия | Обоснование                                         |
| ------------------- | --------------- | --------------------------------------------------- |
| `data-analysis`     | `A2`            | чтение агрегатов SQLite/`raw_responses`, обратимо   |
| `hypothesis-draft`  | `A1`            | кодифицирует текущее поведение ANA-128 (черновики)  |
| `experiment-launch` | `A0`            | расходует ресурс/время команды, меняет ход проверки |
| `pricing`           | `A0`            | прямое влияние на выручку                           |
| `budget`            | `A0`            | деньги наружу                                       |
| `public-comms`      | `A0`            | репутационный риск, внешне необратимо               |
| `strategic`         | `A0`            | долгий горизонт, дорогая ошибка                     |
| `legal`             | `A0`            | не делегируется ИИ никогда                          |

**Требуемый уровень автономии (как он выводится):** в MVP каждое AI-решение исполняется
на одном и том же уровне — `A1`: ИИ записывает черновики сам, PM ревьюит постфактум
(поведение ANA-128). Модель пока не выводит требуемый уровень из содержимого решения;
`assessDecisionAutonomy` фиксирует его константой `required = 'A1'` для любого
классифицированного типа. (Пер-решённый требуемый уровень — например, `data-analysis`
запрос, требующий `A2` при автоисполнении, — вне scope и появится вместе с `A2`.)

**Правила эскалации:** AI-решение (`source = 'ai'`) помечается
`escalation = { required: true, reason }` тогда и только тогда, когда требуемый уровень
выше максимума его типа, либо тип не определён. Контракт детерминированный:

- тип классифицирован → `escalation.required = (максимум типа < A1)`, причина
  `'autonomy-exceeded'`; следствия (фиксируются тестами матрицы): 6 типов с максимумом
  `A0` эскалируются **всегда** (ИИ может их только предложить, принять — PM),
  `hypothesis-draft` (`A1`) и `data-analysis` (`A2`) — **не** эскалируются
  (для `data-analysis` запас до `A2` — задел на будущее автоисполнение);
- тип не определён (`decision_type = NULL`: неклассифицируемый текст или строка,
  пропущенная бэкфиллом) → `required = true`, причина `'unclassified-type'`, трактовка
  `strategic` (максимум `A0`).

`reason` — машинно-читаемый код из фиксированного enum'а:
`'autonomy-exceeded' | 'unclassified-type'`. API отдаёт сырой код; в `/app/decisions`
бейдж «требует PM-эскалации», текст причины получается маппингом кода в строки i18n
(ru и en).

**Вне scope:**

- автоматические действия ИИ уровня `A2` (только моделируется: матрица и лимиты как
  контракт; ни один код не исполняет решения без PM);
- RBAC сверх существующего (`openspec/specs/auth/spec.md`);
- ручное редактирование `decision_type` (UI + API): исправление классификации — правкой
  классификатора в коде (см. риски §5), поле в MVP не редактируемо;
- история изменений матрицы (матрица статична в коде; динамическая настройка — потом);
- отображение автономии в DOCX/PDF-отчёте (render-путь отчёта не меняется).

## 3. Критерии приёмки (измеримые)

- [ ] `@pca/shared` экспортирует таксономию: ровно 8 типов решений, 3 уровня (`A0`–`A2`),
      статическую матрицу «тип → макс. автономия», enum причин эскалации и чистую
      функцию оценки эскалации
- [ ] Матрица зафиксирована тестами: `data-analysis → A2`, `hypothesis-draft → A1`,
      остальные 6 типов → `A0` (`legal` — никогда не делегируется); следствия правил
      эскалации: `data-analysis` и `hypothesis-draft` не эскалируются (требуемый `A1` ≤
      максимум), каждый из 6 типов с максимумом `A0` → `'autonomy-exceeded'`
- [ ] ai-autopopulate классифицирует каждое создаваемое AI-решение в один из 8 типов;
      неклассифицируемый текст → тип не записывается (`decision_type = NULL`), оценка
      трактует его консервативно (`strategic` → максимум `A0`) + причина эскалации
      (код `'unclassified-type'`)
- [ ] Миграция 020 бэкфилл-ит legacy AI-строки (`source = 'ai'`, `decision_type = NULL`)
      в `hypothesis-draft`: на деплое ни одна существующая AI-строка не превращается в
      бейдж «требует PM-эскалации». Тесты legacy-популяции: (а) миграция — AI-строка,
      созданная до 020, после применения получает `hypothesis-draft`; (б) API — AI-строка
      с `decision_type = NULL` (неклассифицируемая или пропущенная бэкфиллом) оценивается
      консервативно (`strategic`/`A0`, `'unclassified-type'`); (в) UI — такая запись
      показывает бейдж эскалации с причиной
- [ ] `GET /api/decisions` возвращает для каждого AI-решения блок `autonomy`
      (тип, допустимый максимум, требуемый уровень, `escalation` + причина); для
      `manual`-решений блока нет
- [ ] `/app/decisions`: бейдж уровня автономии у каждого AI-решения; бейдж
      «требует PM-эскалации» + причина для `escalation`-решений; строки i18n в ru И en
- [ ] A2 нигде не исполняется: в коде нет действий, выполняемых без PM (проверка ревью)
- [ ] Инварианты: render-путь отчёта не меняется (без `Date.now()`/LLM-вызовов);
      «заявка ≠ оплата» не затрагивается; TypeScript strict без `any`; 100% покрытие
      новой логики (ADR-006)
- [ ] CI зелёный, включая `openspec validate --all --strict`

## 4. Влияние

- **Shared (`@pca/shared`):** новый `src/types/decision-autonomy.ts` — типы
  (`DecisionType`, `AutonomyLevel`, `AutonomyEscalationReason`, `AutonomyMatrix`,
  `AutonomyAssessment`), константа матрицы, enum причин эскалации
  (`'autonomy-exceeded' | 'unclassified-type'`), чистая функция
  `assessDecisionAutonomy`: вход `{ source, decisionType }` → выход с трактовкой типа,
  максимумом, константным `required = 'A1'` и `escalation` (см. «Правила эскалации» §2).
  Без новых зависимостей.
- **Данные / БД:** миграция 020 — nullable-колонка `decisions.decision_type`
  **и бэкфилл legacy-строк**: `UPDATE decisions SET decision_type = 'hypothesis-draft'
WHERE source = 'ai' AND decision_type IS NULL`. Обоснование: на момент деплоя каждая
  AI-строка создана ai-autopopulate (ANA-128, с v3.4.6) как черновик проверки гипотезы —
  тип известен из происхождения записи, поэтому без LLM и без дублирования
  keyword-классификатора в SQL. Иначе (без бэкфилла) каждая legacy-строка получила бы
  трактовку `strategic`/`A0` + причину `'unclassified-type'` и превратилась бы в бейдж
  «требует PM-эскалации» — волна однотипных бейджей, против которой и направлена модель
  (п. 2 §1). После миграции `NULL` остаётся только у неклассифицируемых строк; история
  по дням не затрагивается.
- **API:** `GET /api/decisions` обогащается блоком `autonomy` для `source = 'ai'`;
  расчёт детерминированный (тип из БД + статическая матрица), без LLM-вызовов.
- **Backend:** `ai-autopopulate.ts` — классификатор типа решения из текста AI-ответа;
  `decisions-repo.ts` — сохранение/чтение `decisionType`.
- **UI:** `/app/decisions` — бейджи уровня автономии и эскалации с причиной
  (title/tooltip), i18n ru+en; существующий бейдж «AI» сохраняется.
- **Конфиг / env:** новых переменных нет (матрица — константа в `shared`).
- **Документация:** README (RU+EN) — раздел про модель; `docs/help/{ru,en}` — статья
  «Решения» дополняется правилами автономии; CHANGELOG.

## 5. Риски и альтернативы

- **Риски:**
  - Матрица слишком строгая → AI-черновики копятся без пользы. Ловим метрикой из
    Decision Log (доля исходов `green` по гипотезам до/после, WoW) — без неё решение о
    пересмотре матрицы не принимаем (методология Decision Log).
  - Классификатор типов ошибается → детерминированный keyword-классификатор делаем
    консервативным: при неоднозначности выбирается тип с **более низким** максимумом, так
    что худший случай — лишняя эскалация (PM-шум), а не пропущенная. Сомнение PM видит в
    бейдже. Ручного редактирования `decision_type` в MVP **нет** (вне scope): исправление
    систематической ошибки — правкой классификатора/матрицы в коде и релизом; разовые
    промахи нейтрализуются консервативностью и метрикой Decision Log.
  - Legacy-данные при деплое → закрываем бэкфиллом в миграции 020 (см. §4): существующие
    AI-строки получают `hypothesis-draft` и не порождают волну бейджей
    «требует PM-эскалации»; приёмочные критерии и тесты фиксируют поведение legacy-популяции.
  - Матрица в коде, а не в настройках → пересмотр требует релиза. Осознанно для MVP:
    статичность = воспроизводимость оценки; вынос в `app_settings` — отдельная задача.
  - Захламление UI бейджами → бейджи только для `source = 'ai'`, escalation-бейдж один;
    бэкфилл legacy-строк (см. §4) убирает основной источник однотипных эскалаций.
- **Альтернативы:**
  - Динамическая матрица в БД/настройках — отклонено для MVP (вне scope: история
    изменений матрицы, нужен UI управления).
  - Всё считать `A0` (ИИ только предлагает) — отклонено: теряем уже работающее и
    полезное автопополнение ANA-128, которое фактически работает как `A1`.
  - Автоисполнение `A2` — отклонено (вне scope по п.7 админ-репорта); модель только
    готовит контракт на будущее.

## 6. Открытые вопросы

- Нет блокирующих. При реализации уточнить конкретные лимиты `A2` для `data-analysis`
  (частота/объём) — значения ни на что не влияют, пока автоисполнение вне scope.
